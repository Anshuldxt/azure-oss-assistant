# OSS Assistant

A multi-vendor RAN inventory console: load your daily OSS `report.zip`
and look up a single physical NE to see its GSM / UMTS / LTE / NR
cells, IP & VLAN assignment, and S1 transport status in one dashboard.

```
oss-assistant/
├── .github/workflows/
│   └── deploy-azure.yml    CI/CD: builds + deploys to Azure Container Apps on push to main
├── backend/                FastAPI + pandas API (parses CSVs, holds the NE index)
│   ├── app/
│   │   ├── main.py         routes: /api/ingest/zip, /api/ingest/csv, /api/search, /api/ne/{name}, /api/stats
│   │   ├── config.py       vendor/column-mapping config (Huawei + Ericsson done, ZTE stubbed)
│   │   ├── parsers.py      CSV/txt/xlsx detection + row-to-NE indexing (pandas, chunked)
│   │   └── store.py        in-memory NE index
│   └── requirements.txt
├── frontend/
│   └── index.html          dashboard UI, talks to the API over fetch()
├── Dockerfile               single-container build: API + frontend served together
└── AZURE_DEPLOY.md          one-time Azure setup for the CI/CD workflow
```

The frontend is served by the backend itself (see `app.mount(...)` at
the bottom of `main.py`), so the whole app is one container, one port,
one URL — no separate frontend host or CORS setup needed.

## Deploying to Azure (CI/CD)

Push to `main` and GitHub Actions builds the image and deploys it to
Azure Container Apps automatically. One-time setup (Azure resources +
GitHub secrets) is in **[AZURE_DEPLOY.md](./AZURE_DEPLOY.md)** — do
that first, then every push after that redeploys automatically.

## Running it locally

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Then open **http://localhost:8000** in a browser — the backend now
serves the frontend itself. (You can still open `frontend/index.html`
directly instead if you want the frontend and backend on different
hosts/ports; it defaults to same-origin but the "API" field in the top
bar is editable.)

Drop your `report.zip` on the upload panel, or upload individual CSVs.
Files named `*_BFKT.csv` are skipped automatically, per the MOP. Once
loaded, search for an NE name (or a BSC/RNC-side alias) and hit Enter.

## API quick reference

| Method | Path              | Purpose                                   |
|--------|-------------------|--------------------------------------------|
| POST   | `/api/ingest/zip` | upload the whole daily `report.zip`        |
| POST   | `/api/ingest/csv` | upload a single CSV                        |
| GET    | `/api/stats`      | totals across the loaded dataset           |
| GET    | `/api/search?q=`  | NE name / alias autocomplete               |
| GET    | `/api/ne/{name}`  | full dashboard payload for one NE          |
| POST   | `/api/reset`      | clear the in-memory index                  |
| GET    | `/api/vendors`    | list configured vendor profiles            |

Interactive API docs are auto-generated by FastAPI at `/docs` once the
server is running.

## Data mapping notes

**Huawei**
- **DEVIP, VLAN, LTE S1** column mappings were verified against real
  sample CSVs from the report bundle.
- **GSM, LTE, NR, UMTS, Ne_Report** resolvers are built from the column
  layouts described in the MOP document — the bundle used to build
  this only included `*_summary_output` files for those datasets, not
  the actual `*_combine.csv` detail files. Once you have a real export,
  drop it in; if a column name doesn't match, adjust the alias list for
  that field in `backend/app/config.py` (no other code needs to change).
- GSM cells resolve their real NE from the `Site Name` column
  (`GBTS@NE` format); UMTS cells resolve it from `NodeB Name`
  (`NodeB@NE`, or the whole value if there's no `@`). Both aliases are
  kept searchable in the frontend.

**Ericsson** — verified against real report bundles, three of them so far:
- *Execution Report* (`ENM*.txt` cmedit dumps + `NetworkDumpAuditReport*.xlsx`
  + `MmeStatusReport*.xlsx`): NE inventory (RadioNode/RBS/ERBS), IP + sync
  status, base station IDs, MME/S1 transport status, and 2G BSC/site
  inventory. The `ENM*.txt` files here concatenate many separate `cmedit`
  command outputs per file (some with a clean header row, some without);
  only the header-bearing blocks are parsed, headerless ones are reported
  as skipped rather than guessed.
- *Network Cell Status Report* (`ENM*.txt` + `Network Cell Status
  Output*.xlsx`): per-cell LTE (`EUtranCellFDD`/`EUtranCellTDD`), NR
  (`NRCellDU`), and UMTS (`UtranCell`) admin/operational status. **This
  bundle's xlsx and raw txt files describe the same cells** — uploading
  both (e.g. dropping the whole zip) is fine and won't double-count,
  because cell records are deduplicated per (NE, cell ID) in
  `store.already_have_cell()`. That dedup also protects against any
  future overlapping source for the same vendor.
- Multiple Ericsson files enrich the *same* NE record instead of
  overwriting it — `store.merge_ne_report()` only overwrites a field if
  the new value is non-empty, so e.g. the NE-inventory dump and the
  audit xlsx both contribute fields to one merged `neReport`.
- No per-cell GSM (2G) admin/operational status was present in either
  bundle — only BSC/site/sector inventory. `RSITE` (the GSM site name)
  is also its own namespace and isn't guaranteed to align with the
  4G/5G `NodeId` at the same physical location.
- IubLink transport records (Iub admin/oper state) aren't joined into
  the UMTS cell rows yet — would need a second merge pass keyed by
  `RncFunctionId`, similar to `merge_ne_report`.

## Adding a vendor (Ericsson, ZTE, ...)

Everything vendor-specific lives in `backend/app/config.py`. Copy the
`"huawei"` entry in `VENDOR_PROFILES`, rename it, and update:

- `detect` — which normalized column headers identify this dataset for
  this vendor
- `fields` — canonical field → list of that vendor's column name(s)
- `ne_from_split` — only needed if the real NE name is embedded inside
  another column (as with Huawei's GSM/UMTS exports)

Nothing in `main.py`, `parsers.py`, or the frontend needs to change —
they're all driven by this config.

## Scaling notes

The NE index is currently an in-memory Python dict living inside a
single `uvicorn` process (see `backend/app/store.py`). That's enough
for one team loading one daily zip. If you need it to survive restarts,
run multiple workers, or share state across machines, swap `Store` for
a Redis- or SQLite-backed implementation — the API layer only calls
`store.ensure_ne()`, `store.get_ne()`, `store.search()`, etc., so that's
the only file that needs to change.
